# Idempotency contract

Implements [ADR-0008](../../docs/adr/ADR-0008-idempotency.md).

Three mechanisms, covering three different failure modes. No single mechanism
covers all of them, which is why there are three rather than one.

| Layer | Mechanism | Failure mode it covers |
|---|---|---|
| **Default shape** | `DECLARATIVE` — desired state, not an action | Makes idempotency a *structural* property rather than a mechanism someone can forget |
| **Conflict layer** | `MONOTONIC` versioned conditional writes | Out-of-order safety, **and anti-rollback as a security control** |
| **Ceremony layer** | Client-generated idempotency keys + a bounded server dedup log | *"Did my pairing confirmation land?"* — the one question the other two cannot answer |

---

## 1. Which commands require an idempotency key

`CEREMONY` class — an **action with an outcome**. Key **REQUIRED**.

| Command | Dedup window | Why a ceremony |
|---|---|---|
| `RegisterDevice` | 24 h | A uniqueness-establishing commit. Key derived from a **device-local enrolment nonce**, so a retry after a lost response returns the *same* `device_id` |
| `BeginPairing` | 24 h | A duplicate initiate MUST return the **original** `pairing_id`, never mint a second |
| `CompletePairing` | 24 h | **The RQ-3 case.** A timed-out client re-sends the same key and learns the recorded outcome. This is what prevents asymmetric trust |
| `CancelPairing` | 24 h | Burns a single-use `pairing_id`; a duplicate must not burn a second |
| `RevokePairing` | 24 h | An action on a relationship |
| `RevokeDevice` | 24 h | Re-revoking is a no-op; **un-revoking is impossible by construction** |
| `RotateDeviceCredential` | 24 h | A duplicate rotation MUST NOT create a second successor identity |
| `PutPolicy` | 24 h | Authorship of a new signed version |

`DECLARATIVE` class — **desired state**. No key; guarded by `if_version`.

`UpdateDeviceMetadata`, `PutRouteAdvertisement`, `WithdrawRouteAdvertisement`,
`PutExitNodeOffer`, `WithdrawExitNodeOffer`, `GetStateDocument`,
`DiscoverPeers`, `SubscribeEvents`.

`REGISTER` class — **last-writer-wins, loss-tolerant, no dedup log**.

`PublishPresence`, `HealthSample`. Idempotent by construction: they are state
assertions, not commands.

**Relay flow open** is a ceremony with a **5-minute** window rather than 24 h,
scoped to `(session_id, relay_id)`: flows are short-lived, and a duplicate open
MUST return the existing flow handle rather than allocate a second — which is
what prevents relay capacity leaks.

**Explicitly non-idempotent, and the only one:** **kill-switch disengage**.
[ADR-0008](../../docs/adr/ADR-0008-idempotency.md) §11.4 — making *"stop
protecting me"* replay-safe and auto-retryable **is** the silent-fallback defect.
It requires a fresh, explicit, authenticated local Owner action every time, is
never auto-retried, is never triggered by reconciliation, and emits a security
event. It has no command in this contract set at all: it is a local management
action ([ADR-0017](../../docs/adr/ADR-0017-local-management-interface.md)),
`MGMT.DISARM_REQUIRES_LOCAL_AUTH`.

## 2. Key format and generation

- **Type:** opaque `bytes`, 16–64 bytes.
- **Minimum entropy:** **≥128 bits** ([ADR-0008](../../docs/adr/ADR-0008-idempotency.md) N-4).
- **Generated by:** the **client**, never the server. A server-generated key
  cannot survive the round trip it exists to protect.
- **Dedup scope:** `(authenticated DeviceIdentity, idempotency_key)`.
- **Carried in:** `MessageMetadata.idempotency_key`.

**A key is not a capability.** It confers no authorization. Because lookup is
scoped to the authenticated caller, one device cannot probe or replay another
device's outcomes by guessing keys. The entropy requirement makes cross-caller
collision negligible *even though* scoping already prevents it.

**Retry discipline:** a retry reuses `idempotency_key` and mints a **fresh
`message_id`**. That separation is what lets a support bundle distinguish *"the
client retried once"* from *"the network duplicated it"*.

## 3. Deduplication, retention, and replay

The control plane records `(device_id, idempotency_key) → (outcome, response)`
**durably** for the window, and **replays the recorded response verbatim** for a
duplicate inside it ([ADR-0008](../../docs/adr/ADR-0008-idempotency.md) N-5).

`MutationResult.idempotent_replay` marks the replay, so it is **observable**
without changing the response body — a client that ignores the flag still
behaves correctly, and a support engineer can see that a duplicate was collapsed.

### The window-expiry cliff, and what actually closes it

A duplicate arriving **after** the window is **not** re-executed. It is evaluated
against the version precondition (N-2) and therefore **fails**
([ADR-0008](../../docs/adr/ADR-0008-idempotency.md) N-6).

This is the load-bearing detail. The cliff is closed by **the precondition, not
by a longer window** — which is why `VersionPrecondition` is required on every
declarative mutation and on `CompletePairing`, and why lengthening the dedup
window would be treating a symptom.

**Retention:** 24 h default, a control-plane configuration value rather than a
protocol constant, so it can be raised without a `ProtocolEpoch` bump. The dedup
log is also an information leak — it records what a device did and when — so it
inherits [ADR-0015](../../docs/adr/ADR-0015-observability-and-diagnostics.md)'s
retention rules and **MUST NOT be retained beyond its functional window**.

## 4. Expected response to a duplicate

| Situation | Response |
|---|---|
| Duplicate inside the window | **The original response, verbatim**, with `idempotent_replay = true`. Never a 409, never a fresh execution |
| Duplicate after the window, precondition still satisfiable | Fails the precondition. `precondition_failed` |
| Duplicate after the window, state already changed | Fails the precondition |
| Same key, **different request body** | Rejected. A key names one operation; reusing it for another is a client defect |
| Precondition failure | **The client MUST re-read the current document before the next attempt, not blindly retry.** A blind retry loops |

## 5. Anti-rollback: idempotency as a security control

[ADR-0008](../../docs/adr/ADR-0008-idempotency.md) §7.1 — this is not hygiene.

> **A device MUST reject any state document whose version is lower than the
> version it has already accepted**, and MUST record the rejection as a
> **security event**.

Enforced at the local store, so it holds **even against a compromised or hostile
control plane** — which matters, because the control plane is only semi-trusted.

**Revocation is modelled as a monotone epoch plus a never-shrinking set**
(N-7), never as a mutable `revoked: true/false`. A mutable boolean is precisely
the shape that permits **un-revocation by replaying an older record**. An
operation that would shrink the revoked set is rejected.

Monotone counters in this contract set, each with its own high-water mark:

| Counter | Scope | Lower value ⇒ |
|---|---|---|
| `policy_version` | one TwinNet | rejected; policy rollback attack |
| `trust_epoch` | one TwinNet | `AUTH.TRUST_EPOCH_ROLLBACK` |
| `anchor_version` | one TwinNet | rejected; equal-with-different-content ⇒ `AUTH.TRUST_HISTORY_FORKED` |
| `generation` | one device | rejected (key rollback) |
| `tk_generation` | one device | rejected |
| `advertisement_epoch` | one advertiser | ignored |
| `offer_epoch` | one offerer | ignored |
| `path_epoch` | one Session | ignored |
| `net_seq` | one TwinNet | cursor rejected |
| `map_version` | relay map | rejected |
| `epoch_floor` | operator group | rejected |
| `contract_seq` | network contract | rejected |

**The operational consequence is sharp and correct:** restoring an older
control-plane backup **does not silently rewind devices — it strands them**. The
runbook must include an explicit epoch-bump step
([ADR-0002](../../docs/adr/ADR-0002-control-plane-messaging-and-event-bus.md)
O-2): after a restore, the operator MUST advance the TwinNet's
`revocation_epoch` and every state-document `version` past the highest ever
issued before resuming service. Without it, the fleet presents as a
correctly-diagnosed fail-closed refusal — the right outcome, but it must be *in
the runbook, not discovered*.

## 6. Read-your-writes across the C1/C2 boundary

A mutating C1 response and the C2 event it causes travel on different streams.
Without a guarantee, a device sees *"pairing succeeded"* and then a peer list
that does not contain the peer.

Every mutating response carries `committed_at_net_seq`, and:

> **The client library MUST NOT report the operation complete to the UI until the
> C2 cursor has advanced to or past it.** That is a **protocol obligation, not a
> client convenience** ([docs/protocol.md](../../docs/protocol.md) §5.1).

It works because `net_seq` is allocated **inside the mutating transaction, in the
same log the C2 reader reads** — so the returned position cannot be one that does
not exist or that the reader cannot reach. There is no dual write to lose.

## 7. What is deliberately *not* idempotent

Ephemeral packet and candidate traffic is **not** made idempotent, because the
protocol does not require it and making it so would be actively harmful:

- **Candidates** are an idempotent *set merge* keyed on `(family, kind, addr,
  port)` — a natural property, not a dedup log. Reliable delivery of a stale
  candidate is **worse** than losing it: it guarantees a probe against an
  expired NAT mapping or an address now belonging to someone else.
- **Punch probes** are idempotent because duplicates are harmless and expected.
  A dedup log would add state to the highest-rate, shortest-lived exchange in the
  system.
- **`PathOffer`/`PathAck`** are idempotent by `path_epoch`; re-offering the same
  epoch is a no-op. No key, no log.
- **Presence and health** are permitted to be lost.

## 8. What the tests prove

[`tests/test_semantics.py`](../tests/test_semantics.py) asserts that every
mutating request carries `MessageMetadata` (hence an `idempotency_key` slot),
that every declarative mutation carries a `VersionPrecondition`, that
`VersionPrecondition` is a oneof so "no precondition" is unrepresentable, that
every mutating response carries `MutationResult`, and that `MutationResult`
carries `committed_at_net_seq`, `revocation_epoch` and `idempotent_replay`.

The determinism the objective asks for — *"contract tests must prove that
retryable operations have deterministic idempotency semantics"* — is proven
structurally: a retryable operation **cannot be expressed** in this schema
without the metadata that makes its outcome deterministic.
