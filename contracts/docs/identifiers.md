# Stable identifier rules

For every first-wave resource: type, generation authority, uniqueness scope,
opacity, reuse, and whether the value carries meaning.

**The default is opaque.** Phase 1 makes exactly two identifiers structurally
meaningful, both deliberately, and both self-certifying rather than descriptive.
Every other identifier is a bag of bits whose only property is equality.

## 2. The two meaningful identifiers, and why

### `device_id` and `identity_id` are derived, not assigned

```
identity_id = SHA-256("TwinVPN/DeviceIdentity/v1" || 0x00 || dCBOR(COSE_Key(IK_pub)))
device_id   = identity_id of generation 0
```

[ADR-0007](../../docs/adr/ADR-0007-device-identity-and-pairing.md) N-2, Q1.
Three properties follow, and each is load-bearing somewhere else:

1. **Verifiable offline by any peer.** No lookup, no authority, no network. This
   is what lets two paired devices re-establish a `Session` with the control
   plane entirely down (**I5**, **R-11**).
2. **Unforgeable by the coordination service.** A server-assigned identifier
   would let a semi-trusted coordination service mint a device.
3. **Stable across rotation.** A rotation creates a new `DeviceIdentity` at
   `generation+1` but **does not change `device_id`** — otherwise S-08's
   immutable address allocation would break on every rotation, and every peer's
   cached routes with it.

`RegisterDeviceResp.device_id_echo` is an **echo, never an assignment**. The
device compares it to its own derived value and **aborts with
`AUTH.IDENTITY_MISMATCH` on disagreement**. It must not adopt the server's value.

**Text form.** `"twd1" || base32-lower-nopad(device_id)`. This is a
**presentation form only** and appears in no field of this contract set —
`MessageMetadata.sender_id` is the one place it is written, because that field
carries either a device text form or a fixed infrastructure principal name.

**Human fingerprint.** The leading 100 bits in Crockford base32, five groups of
four. UIs MUST render all twenty characters and MUST NOT offer a truncated
comparison. **The fingerprint MUST NOT be a trust decision input** — trust comes
from the pairing ceremony, not from a human comparing strings.

### `pairing_id` is derived by the joining device

`pairing_id = SHA-256(pairing_secret)[0..15]`, computed by the joining device and
**carried to** the coordination service — not minted by it. It also doubles as
the HKDF salt for the ceremony channel. A server-minted value would break both
roles at once, and would let the rendezvous correlate a handle to a secret it
must never see.

It is **single-use and never reissued, not even after expiry or cancellation**:
reissuing it would reset the five-attempt budget that
[ADR-0007](../../docs/adr/ADR-0007-device-identity-and-pairing.md) N-17 relies on
to make a 9-digit code safe.

## 3. Identifiers that deliberately do not exist

### `peer_id`

A peer is named by its `device_id`. There is no separate peer identity, because
`TrustedPeer` is a *relationship* keyed by
`(local_device_id, peer_device_id)` — a **derived** identity
([docs/architecture.md](../../docs/architecture.md) §3.3). Minting a `peer_id`
would create a second name for a device and therefore a second place to decide
whether it is revoked.

### `gateway_id`

`ExitNode` and `LANGateway` are both identified by "the `device_id` of the
acting device — *derived*". A `Device` is at most one of each. A separate
`gateway_id` would be a second name for one thing, and a peer's revocation
state — the single fact that must revoke access — would then need a join to
apply.

### `device_identity_id` as a separate resource

`identity_id` exists and is modelled, but it is **not a separate resource with
its own lifecycle**: it is an attribute of the current `DeviceIdentity`, and the
resource is the `Device`. Rotation replaces the identity while the device
persists.

## 4. Field semantics: how each metadata identifier is generated and used

### `message_id`

**Unique per emission, including per retransmission of a logically identical
request.** A retry reuses `idempotency_key`, **never** `message_id`.

That separation is the whole point: it is what lets diagnostics distinguish
*"the client retried once"* from *"the network duplicated it"*
([docs/protocol.md](../../docs/protocol.md) §2). Collapsing them would make a
flaky link and a buggy client look identical in a support bundle.

UUIDv7 rather than v4 because it is time-sortable, so a log can be ordered
without a separate timestamp field.

### `correlation_id` versus `causation_id`

They answer different questions and are both required.

- **`correlation_id` — "what is this a reply to?"** A response MUST echo the
  request's `message_id`.
- **`causation_id` — "what made this happen?"** The `message_id` of the message
  whose *processing* produced this one.

They coincide for a direct response. They **differ** whenever an event is a
second-order consequence: a `PolicyBundleUpdated` caused by a `PutPolicyReq`
carries that request's id in both, but a route withdrawal triggered by
*processing* a `DeviceRevoked` carries the revocation event's id in
`causation_id` and has no `correlation_id` at all.

Set by the emitter from the message it is currently processing. **Never
invented, never inherited transitively** — a causation chain is reconstructed by
following one link at a time, which is what keeps it a chain rather than a claim.

### `idempotency_key`

Client-generated, **≥128 bits of randomness**, scoped by the server to the
authenticated `DeviceIdentity`.

**An idempotency key is not a capability.** It confers no authorization, and
dedup lookup is scoped to the caller, so one device cannot probe or replay
another device's outcomes by guessing keys
([ADR-0008](../../docs/adr/ADR-0008-idempotency.md) §7.3). The ≥128-bit
requirement makes cross-caller collision negligible *even though* scoping
already prevents it — belt and braces, because the cost is nil.

For `RegisterDevice` the key is derived from a **device-local enrolment nonce**,
so a retry after a lost response returns the *same* `device_id` rather than
creating a duplicate device. Duplicate-device-on-retry is a classic failure of
this product category.

### `causality_token`

Opaque, minted by the control plane, **echoed by devices, never parsed by
them**. Devices store the newest per `twinnet_id` and send it back on every C1
request.

This is deliberately the weakest possible client-side contract: any client-side
interpretation of causality metadata becomes a compatibility landmine across
version boundaries. Internally it carries monotonic-read constraints across
replica failover, and that structure is the control plane's business.

### `net_seq`

Allocated by a per-TwinNet monotone counter **inside the same transaction that
commits the state mutation it describes**
([ADR-0002](../../docs/adr/ADR-0002-control-plane-messaging-and-event-bus.md)
N-3). Non-zero **only** on a durable C2 event.

This is what makes read-your-writes structural rather than engineered: a
returned `committed_at_net_seq` cannot name a position that does not exist or
that the reader cannot reach, because there is no second write to lose.

### `pair_tag`

```
pair_tag = HKDF-Expand(RelayPairKey, "tag" || relay_id || bucket, 16)
```

Scoped to **one `relay_id` and one 10-minute bucket**; both peers accept
`bucket`, `bucket−1` and `bucket+1` for skew. One-way, so a relay that holds it
learns nothing about who the peers are. A tag observed at one relay is useless at
another, and it rotates every bucket.

This replaced a `peer_key_id` field
([docs/protocol.md](../../docs/protocol.md) §16 row 21, **withdrawn**), which
would have told the relay which two devices are talking.

## 5. Validation

Every size in the table is **exact and enforced on receipt**. A length mismatch
is `PROTO.MALFORMED_MESSAGE` — never a truncation and never a pad, because both
would silently convert one identifier into another.

Machine-readable sizes: [`registry/limits.json`](../registry/limits.json),
section `identifiers`. Asserted by
[`tests/test_semantics.py`](../tests/test_semantics.py).

Binary identifiers are `bytes`, never `string`: a textual identifier admits case,
encoding and padding variance at a boundary where set membership must be exact.
